# Wiki 与知识图谱验证复盘

日期：2026-06-27

适用对象：后续继续验证、维护或扩展这套知识库方案的同事。

相关目录：`llm-wiki-kg-demo`

## 一句话结论

这次验证说明两件事：

- 自研 Wiki/JSONL demo 适合做可控、可校验、可导出的轻量知识图谱底座。
- Karpathy LLM Wiki 适合做 Obsidian 内的日常资料摄入、双向链接和自然语言查询。

推荐组合使用：用 Karpathy LLM Wiki 提升日常整理效率，用 JSONL 和校验脚本保证结构化、可追溯和后续图谱化。

## 这次做过什么

本轮实际做了两类验证。

第一类是自研轻量方案：

- 建了 `sources/`、`wiki/`、`graph/`、`scripts/`、`reports/` 目录。
- 用假产品、假案例资料模拟知识来源。
- 手工整理 Obsidian 风格 Wiki 页面。
- 用 JSONL 表达实体、关系、证据。
- 写了 `validate_graph.py` 校验死链、缺失证据、非法 JSONL、悬空实体 ID。
- 写了 `model_smoke_test.py` 测 MiniMax-M3 是否能做结构化抽取。

第二类是开源组件验证：

- 安装 Obsidian。
- 安装 Karpathy LLM Wiki 插件。
- 配置 MiniMax 国内 Token Plan endpoint。
- 用假 POC 资料实测新增、修改、查询、删除行为。
- 记录 Karpathy 生成的 source summary、entity 页面、concept 页面。
- 验证 Obsidian 内的 Query Wiki 能基于 Wiki 回答问题。

## 为什么要分两套看

不要把“开源插件能自动生成 Wiki”误解成“企业知识图谱已经建好了”。

两套方案解决的问题不一样：

| 维度 | 自研 Wiki/JSONL demo | Karpathy LLM Wiki |
| --- | --- | --- |
| 核心价值 | 结构可控、可校验、方便导出 | 日常摄入快、双链自动化、查询方便 |
| 适合谁用 | 工程化、后续图谱管道、CI 校验 | 写笔记的人、产品/方案/交付同事 |
| 输出形态 | Markdown + JSONL | Obsidian Wiki 页面 |
| 稳定性 | 高，规则自己控制 | 中，LLM 会改写/补写页面 |
| 查询体验 | 需要另接检索或脚本 | 插件自带 Query Wiki |
| 删除治理 | 可以按规则脚本化 | 不自动级联删除，需要软删除 |
| 后续扩展 | 适合接 Neo4j/GraphRAG | 适合沉淀来源和链接关系 |

实际最佳路径不是二选一，而是先用 Karpathy 提高资料整理效率，再把稳定后的事实抽到 JSONL/图数据库。

## 自研 Wiki/JSONL 的经验

### 适合做什么

适合用来验证“知识图谱最小闭环”：

- 一条事实来自哪里。
- 一个实体有哪些来源。
- 一个关系有没有证据。
- Wiki 双链有没有死链。
- 后续能不能导出到图数据库。

它不依赖 Obsidian 插件，也不依赖某个 LLM 的生成结果。只要 Markdown 和 JSONL 在，校验脚本就能跑。

### 关键目录

```text
llm-wiki-kg-demo/
  sources/     原始资料，尽量不直接覆盖历史事实。
  wiki/        给人读的 Wiki 页面，使用 Obsidian 双链。
  graph/       结构化实体、关系、证据。
  scripts/     校验脚本和模型测试脚本。
  reports/     验证报告。
```

### 关键规则

- `sources/` 是事实来源，不能只改生成页而不改来源。
- `wiki/` 是阅读层，可以有解释、摘要和双链。
- `graph/` 是结构化层，必须能校验。
- 每条关系都应该能追到 evidence。
- 每次批量改 Wiki 后，都跑一次 `validate_graph.py`。
- 不把 API Key、Obsidian 本地配置、个人缓存提交到 Git。

### 优点

- 可控，不会被插件自动改写。
- 适合 CI。
- 适合导出。
- 出问题容易定位。
- 对后续知识图谱建设更直接。

### 局限

- 手工成本高。
- 没有现成的查询 UI。
- 不会自动抽 entity/concept。
- 需要团队自己维护 schema 和校验脚本。

## Karpathy LLM Wiki 的经验

### 适合做什么

适合做日常知识整理：

- 把一篇 Markdown 自动摄入成 Wiki。
- 自动生成 source summary。
- 自动识别 entity 和 concept。
- 自动建立 Obsidian 双向链接。
- 用 Query Wiki 直接问知识库。

这对于会议纪要、客户需求、方案边界、产品说明、案例复盘很有价值。

### 本次实际跑通的配置

```bash
OPENAI_BASE_URL=https://api.minimaxi.com/v1
MODEL=MiniMax-M3
```

API Key 只放本机，不写进仓库。

Obsidian 插件配置在 `.obsidian/` 下，当前 demo 已忽略该目录。

### 本次实测通过的动作

新增：

- 新建 `sources/daily/2026-06-27-retail-edge-poc.md`。
- 在 Obsidian 打开源文件。
- 点击“摄入当前文件”。
- 插件生成 source summary、entity 页、concept 页。

修改：

- 在同一源文件追加“2026-06-27 变更记录”。
- 重新摄入。
- 新增验收指标写入 Wiki。

查询：

- 打开 Query Wiki。
- 提问：`华东零售门店边缘推理 POC 的验收指标和报价边界是什么？`
- 插件正确回答三项验收指标和报价边界，并给出 Obsidian 引用链接。

删除：

- 临时移走源文件后，已生成 Wiki 页仍然存在。
- 结论：不能依赖自动级联删除。

### 观察到的优点

- 上手快，能让非工程同事直接在 Obsidian 里用。
- 自动生成链接和摘要，节省大量手工整理时间。
- 查询体验比纯 Markdown 好。
- 能把零散资料变成有路径、有链接、有引用的 Wiki。
- 对后续知识图谱有帮助，因为实体页、概念页、source 页已经形成了半结构化资料。

### 观察到的问题

1. 重摄入慢

小文件第二次重摄入耗时 7 分钟。原因是插件会重新处理相关实体和概念，不只是更新一页摘要。

2. 可能产生重复实体

仓库原来已有产品页：

- `wiki/products/品原AI一体机.md`
- `wiki/products/AI原生推理平台.md`

Karpathy 又生成实体页：

- `wiki/entities/品原-AI-一体机.md`
- `wiki/entities/AI-原生推理平台.md`

这不是死链，但会造成“产品页”和“实体页”重复表达。

3. 生成页会被改写

重新摄入时，插件可能补写或改写已有 entity/concept 页面。正式页面要有 review 和保护规则。

4. 删除不会自动清理

源文件删除后，生成页还在。必须有软删除、废弃和清理流程。

5. 校验脚本要兼容 Obsidian 路径链接

Karpathy 会生成 `[[entities/xxx]]`、`[[sources/xxx]]` 这种路径型链接。原先只按文件名 stem 校验会误判死链，所以已经升级了 `validate_graph.py`。

## 给同事的推荐流程

### 第 1 步：准备资料

把资料先放到 `sources/`，不要直接写到 `wiki/`。

推荐目录：

```text
sources/daily/      日常会议纪要、客户沟通记录
sources/cases/      项目案例、POC、交付复盘
sources/products/   产品说明、能力说明
sources/policies/   规则、边界、标准口径
```

文件建议：

- 一个文件只讲一个主题。
- 标题写清楚对象和场景。
- 关键事实写成短段落或列表。
- 不要混入密钥、账号、客户敏感信息。
- 资料如果是假的或脱敏的，要明确标注。

### 第 2 步：用 Karpathy 摄入

在 Obsidian 中打开源文件，点击“摄入当前文件”。

摄入后检查：

- source summary 是否保留来源。
- entity 是否命名合理。
- concept 是否过多或过泛。
- 是否和已有产品页/实体页重复。
- 是否出现明显事实错误。

### 第 3 步：用问题验证

摄入后立刻问几个业务问题，不要只看是否生成文件。

示例：

- `这个项目的验收指标是什么？`
- `报价边界不包含哪些内容？`
- `这个产品能力在哪些案例中出现过？`
- `这个方案依赖哪些组件？`
- `有没有不承诺交付的范围？`

如果 Query Wiki 答不上来，通常说明：

- 源资料写得太散。
- 关键事实没有被抽到 entity/concept。
- 页面命名不一致。
- 需要人工补链或重新摄入。

### 第 4 步：修改资料

资料变更时，优先改 `sources/`，再重新摄入。

不要只改生成页，因为后续追溯会断。

推荐写法：

```markdown
## 2026-06-27 变更记录

- 新增验收指标：平均推理时延、离线缓存保留时长、告警误报率。
- 离线缓存保留时长不少于 24 小时。
- 不承诺替换客户已有视频管理平台。
```

### 第 5 步：删除或废弃

不要直接删源文件。

先加废弃记录：

```markdown
## 废弃记录

- 状态：已废弃
- 废弃日期：2026-06-27
- 废弃原因：客户验收口径已被新版方案替代
- 替代来源：[[sources/daily/新版文件]]
```

然后再决定是否清理生成页。

清理后必须跑：

```bash
python3 llm-wiki-kg-demo/scripts/validate_graph.py llm-wiki-kg-demo
```

### 第 6 步：导出稳定事实

当一批 Wiki 内容稳定后，再抽到 `graph/`：

- `graph/entities.jsonl`
- `graph/relations.jsonl`
- `graph/evidence.jsonl`

只有经过 review 的稳定事实才进入 graph。

## 必须遵守的规则

### 安全规则

- 不提交 API Key。
- 不提交 `.obsidian/`。
- 不把客户敏感信息放进 demo。
- 不把真实内部材料直接推到公开 GitHub。
- 不在报告里粘贴完整密钥、token、cookie。

### 内容规则

- 事实先进入 `sources/`。
- 生成页只作为 Wiki 阅读层。
- 重要事实必须有来源。
- 修改事实要保留日期。
- 废弃事实要保留替代来源。

### 工程规则

- 每次批量修改后跑校验脚本。
- 生成页可以提交，但 Obsidian 配置不提交。
- 脚本输出报告可以提交，但不能含密钥。
- 如果校验脚本误报，要先判断链接风格，不要直接删页面。

## 不要做什么

- 不要把 Karpathy 生成结果直接当正式事实库。
- 不要认为 Query Wiki 答对一次就代表图谱质量合格。
- 不要让插件自动摄入大量真实资料后不 review。
- 不要直接删除源文件期待 Wiki 自动清理。
- 不要把所有资料都塞进一篇长 Markdown。
- 不要混用多个实体命名，例如同一个产品一会儿叫 `品原AI一体机`，一会儿叫 `品原-AI-一体机`。

## 常见问题和处理办法

### 插件连接模型失败

先确认 endpoint。

国内 Token Plan 用：

```bash
https://api.minimaxi.com/v1
```

不要误用国际站 endpoint。

再确认模型：

```bash
MiniMax-M3
```

最后确认 key 是本机有效 key，不要从聊天记录里复制错误版本。

### 生成了重复实体

先不要删。

处理顺序：

1. 看两个页面是否都被引用。
2. 确定主页面。
3. 在重复页面写清楚 alias 或合并说明。
4. 修改源资料里的命名。
5. 重新摄入或手工补链。
6. 跑校验。

### 查询回答不准

先看引用页面。

如果引用页面没有事实，说明摄入没有抽到。

如果引用页面有事实但回答错，说明查询生成质量问题。

处理方式：

- 把关键事实写得更明确。
- 拆小源文件。
- 补充 entity/concept 页面。
- 降低一次性摄入量。

### 校验脚本报死链

先判断是哪种链接：

- `[[页面名]]`
- `[[entities/页面名]]`
- `[[entities/页面名.md]]`
- `[[sources/daily/文件名]]`

如果页面实际存在，是校验脚本兼容问题。

如果页面不存在，才是真死链。

## 下一阶段建议

建议做一个 1 周小规模试运行：

- 准备 10 到 20 篇脱敏资料。
- 覆盖产品、案例、报价边界、验收指标、客户问题。
- 每天新增 2 到 3 篇。
- 每天做一次修改和查询。
- 每周做一次废弃和清理。
- 每次结束跑 `validate_graph.py`。

观察指标：

- 平均摄入耗时。
- 重复实体数量。
- 查询命中率。
- 需要人工修正的页面数量。
- 死链数量。
- 可导出到 JSONL 的稳定事实数量。

如果这些指标可控，再进入正式知识图谱阶段。

## 最终建议

当前阶段不要急着上重型知识图谱平台。

先把这条轻量链路跑稳：

```text
Markdown 源资料 -> Karpathy LLM Wiki -> 人工 review -> JSONL 图谱 -> 校验脚本 -> 后续图数据库/GraphRAG
```

这条路径的优势是投入小、能快速看到效果，也不会过早被复杂平台锁死。
